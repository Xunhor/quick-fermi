# AGENTS.md — BOOMO

## 1. CONTEXTO DO PROJETO

A Boomo é uma empresa brasileira de sites profissionais por assinatura.

O produto principal é simples:

> A Boomo cria, publica e mantém sites profissionais para empresas, profissionais autônomos e negócios locais através de uma assinatura mensal.

O objetivo do projeto é transmitir:

* profissionalismo;
* confiança;
* simplicidade;
* qualidade;
* sofisticação;
* clareza;
* proximidade;
* competência técnica sem excesso de tecnicismo.

A Boomo NÃO deve parecer uma empresa de inteligência artificial.

A Boomo NÃO deve parecer um projeto experimental.

A Boomo NÃO deve parecer uma landing page genérica criada automaticamente.

A Boomo deve parecer um produto digital real, cuidadosamente projetado por uma equipe profissional.

---

# 2. REGRA ABSOLUTA — PRESERVAR O PROJETO

Antes de modificar qualquer código:

1. Leia a estrutura atual do projeto.
2. Identifique os componentes existentes.
3. Identifique os estilos existentes.
4. Identifique as páginas existentes.
5. Identifique as integrações existentes.
6. Identifique os templates existentes.
7. Identifique os links e CTAs existentes.
8. Identifique as dependências existentes.
9. Verifique como o projeto é executado e buildado.
10. Não reescreva componentes sem necessidade.

### Nunca:

* recrie o projeto inteiro;
* substitua a arquitetura existente sem necessidade;
* troque o framework;
* troque a biblioteca de componentes;
* remova dependências apenas por preferência;
* reescreva arquivos inteiros quando uma alteração localizada for suficiente;
* substitua componentes funcionais por versões simplificadas;
* remova funcionalidades existentes;
* altere URLs existentes sem necessidade;
* altere integrações de pagamento;
* altere links do WhatsApp;
* altere preços sem autorização explícita.

A prioridade é:

> **preservar → melhorar → validar.**

Nunca:

> **recriar → simplificar → quebrar.**

---

# 3. REGRA DE OURO PARA O AGENTE

Antes de qualquer alteração significativa, faça uma análise do impacto.

Se uma alteração puder afetar:

* layout;
* responsividade;
* navegação;
* componentes compartilhados;
* rotas;
* templates;
* pagamentos;
* WhatsApp;
* SEO;
* performance;

verifique primeiro onde esses elementos são utilizados.

Não faça alterações destrutivas.

Se houver dúvida sobre uma decisão arquitetural importante, pare e peça confirmação.

---

# 4. IDENTIDADE DA BOOMO

A identidade visual deve ser:

* moderna;
* minimalista;
* premium;
* limpa;
* profissional;
* tecnológica na medida certa;
* humana.

A interface deve parecer projetada por um bom designer de produto.

Evitar aparência de:

* template de startup;
* dashboard SaaS genérico;
* landing page de IA;
* site excessivamente futurista;
* site cheio de gradientes;
* site com excesso de glassmorphism;
* site com excesso de cards;
* site com excesso de animações;
* site genérico produzido por um gerador de landing pages.

---

# 5. PRINCÍPIO: MENOS É MAIS

Não adicionar elementos apenas para preencher espaço.

Não criar:

* cards desnecessários;
* badges desnecessários;
* números gigantes;
* estatísticas inventadas;
* gráficos;
* elementos decorativos aleatórios;
* animações apenas porque são possíveis.

Cada elemento deve ter uma função.

Se um elemento não melhora:

* compreensão;
* confiança;
* conversão;
* navegação;
* estética;

considere removê-lo.

---

# 6. NÃO PARECER FEITO POR IA

Esta é uma das regras mais importantes do projeto.

A interface não deve utilizar padrões visuais óbvios de sites gerados por IA.

Evitar especialmente:

* excesso de gradientes;
* gradientes roxo/azul genéricos;
* glow excessivo;
* textos genéricos de marketing;
* frases como "revolucione seu negócio";
* "solução inovadora";
* "tecnologia de ponta" sem contexto;
* excesso de palavras como "transformar", "potencializar", "elevar", "revolucionar";
* métricas chamativas sem comprovação;
* badges como "AI POWERED";
* elementos flutuantes aleatórios;
* excesso de glassmorphism;
* excesso de sombras;
* bordas exageradas;
* animações contínuas;
* efeitos que parecem demonstração de tecnologia.

A página deve parecer intencional.

---

# 7. COPYWRITING

A comunicação deve ser:

* clara;
* curta;
* humana;
* comercial;
* confiante;
* direta.

Escreva para o dono de uma empresa, não para um desenvolvedor.

O cliente quer saber:

* quanto custa;
* quando fica pronto;
* como funciona;
* o que está incluso;
* quem cuida do site;
* como falar com a Boomo;
* se pode cancelar;
* se o site será profissional.

Não utilizar excesso de termos técnicos.

Tecnologia deve aparecer como benefício ou prova de qualidade.

---

# 8. REGRA SOBRE CLAIMS E MÉTRICAS

Nunca invente métricas.

Nunca invente:

* número de clientes;
* faturamento;
* avaliações;
* depoimentos;
* resultados;
* velocidade;
* PageSpeed;
* uptime;
* conversão;
* número de projetos;
* anos de experiência.

Se uma métrica não estiver comprovada no projeto, não apresente como fato.

Evitar claims como:

> 0.4s garantidos

> Nota 95+ garantida

> 99.9% uptime garantido

a menos que exista uma comprovação técnica real e consistente.

Prefira:

> Performance otimizada.

> Site rápido.

> Estrutura preparada para SEO.

> Hospedagem e SSL inclusos.

---

# 9. TEMPLATES

Os templates são uma parte central da proposta comercial da Boomo.

Não remover.

Não simplificar.

Não substituir por cards genéricos.

Os templates devem continuar sendo apresentados por segmento.

Exemplos atuais:

* Estética;
* Odontologia;
* Advocacia;
* Contabilidade.

Os templates demonstrativos NÃO são clientes reais.

Nunca apresentá-los como clientes reais.

Usar linguagem como:

> Exemplos de sites que podemos criar.

ou:

> Modelos demonstrativos.

---

# 10. CONVERSÃO

O objetivo principal do site é gerar conversas no WhatsApp.

CTAs devem ser claros.

Preferir:

* Quero meu site
* Ver modelos

* Conhecer os planos

Evitar CTAs vagos como:

* Saiba mais
* Explorar
* Descobrir
* Começar jornada

O usuário deve saber exatamente o que acontecerá ao clicar.

# 11. WHATSAPP

"Olá! Quero saber mais sobre os sites da Boomo."

Não criar múltiplos sistemas diferentes de contato.

* depoimentos falsos;

Nunca comunicar a falta de clientes de forma que prejudique a percepção de confiança.

* bordas;
* radius;
* sombras;

Se um card já existe, reutilize-o.

Se um padrão visual já existe, reutilize-o.

Toda alteração visual deve ser validada em:

* mobile;
* tablet;
* desktop.

Nunca assumir que uma alteração desktop funciona automaticamente no mobile.

Verificar:

* overflow horizontal;
* tamanhos de fonte;
* espaçamentos;
* imagens;
* grids;
* cards;
* navegação;
* menus;
* botões;
* CTAs;
* templates.

Mobile é prioridade.

---

# 17. ANIMAÇÕES

Usar animações com moderação.

Animações devem:

* melhorar percepção de qualidade;
* orientar atenção;
* criar feedback;
* tornar a experiência agradável.

Não utilizar animações simplesmente para deixar a página "mais bonita".

Evitar:

* elementos pulando;
* textos piscando;
* excesso de parallax;
* movimentos contínuos;
* efeitos exagerados;
* animações em todos os componentes.

A Boomo deve parecer sofisticada, não chamativa.

---

Priorizar:

* lazy loading;
* CSS eficiente;
* componentes reutilizáveis;
* JavaScript apenas quando necessário;
* carregamento rápido;
* Core Web Vitals.

Não sacrificar performance por efeitos visuais.

# 21. CÓDIGO

Código deve ser:

* simples;
* legível;
* modular;
* reutilizável;
* previsível.

Evitar abstrações desnecessárias.

Não criar componentes de uma única utilização apenas para reduzir algumas linhas de código.

Não criar sistemas complexos quando uma solução simples resolve.

Evitar duplicação quando houver uma abstração natural.

---

# 22. ANTES DE EDITAR

Antes de editar um arquivo:

1. Leia o arquivo.
2. Entenda suas dependências.
3. Identifique componentes relacionados.
4. Verifique se o componente é reutilizado.
5. Faça a menor alteração necessária.

Nunca editar baseado apenas no nome do arquivo.

---

# 23. APÓS EDITAR

Depois de alterações importantes:

1. Rodar lint, se disponível.
2. Rodar build.
3. Corrigir erros de compilação.
4. Verificar console.
5. Verificar rotas.
6. Verificar responsividade.
7. Verificar links.
8. Verificar CTAs.
9. Verificar componentes existentes.

Nunca considerar uma alteração concluída apenas porque o código foi escrito.

---

# 24. REGRA DE NÃO-REGRESSÃO

Uma funcionalidade existente não pode ser quebrada para implementar uma melhoria visual.

Se uma alteração quebrar algo:

> Pare.

Investigue.

Corrija.

Depois continue.

Nunca esconda o problema.

Nunca remova uma funcionalidade apenas porque ela está causando conflito sem primeiro entender sua função.

---

# 25. GIT

Antes de alterações grandes:

* verificar git status;
* verificar branch;
* verificar mudanças pendentes.

Sempre que possível, manter mudanças pequenas e isoladas.

Não apagar histórico.

Não fazer alterações destrutivas sem confirmação.

---

# 26. MODO DE TRABALHO

Para alterações grandes, seguir esta sequência:

### Fase 1 — Análise

Entender o projeto.

### Fase 2 — Plano

Descrever o que será alterado.

### Fase 3 — Implementação

Fazer mudanças pequenas.

### Fase 4 — Validação

Build + lint + inspeção visual.

### Fase 5 — Revisão

Verificar regressões.

### Fase 6 — Entrega

Informar exatamente:

* o que foi alterado;
* quais arquivos foram modificados;
* quais testes foram executados;
* se existem pendências.

---

O agente pode melhorar implementação e UX, mas não deve decidir sozinho:

* preço;
* posicionamento;
* público;
* modelo de negócio;
* benefícios dos planos;
* política comercial;
* política de cancelamento;
* garantias;
* claims;
* estratégia de aquisição.

Quando uma mudança alterar a proposta comercial, pedir autorização.

---

# 28. PRINCÍPIO FINAL

A Boomo deve parecer:

> uma empresa pequena, extremamente cuidadosa e competente.

E não:

> uma grande empresa tentando parecer tecnológica.

E principalmente não:

> um site criado por inteligência artificial.

Cada alteração deve passar por esta pergunta:

**"Isso faria um cliente confiar mais na Boomo?"**

Se a resposta for não, não faça a alteração.

---

# 29. REGRA FINAL DE SEGURANÇA

Se o usuário solicitar uma grande alteração no projeto:

1. Primeiro analisar.
2. Explicar o impacto.
3. Criar um plano.
4. Somente então implementar.

Nunca assumir que "melhorar" significa "reescrever".

**Preserve o que funciona. Melhore o que precisa. Não quebre o que já existe.**

---

# 30. HONESTIDADE ABSOLUTA, TRANSPARÊNCIA E NUNCA ENROLAR OU MENTIR

Esta é uma regra inegociável de conduta do agente:

1. **Nunca enrolar o usuário:** Não use textos prolixos, elogios exagerados ou discursos de marketing para mascarar uma entrega incompleta ou que não atingiu o padrão desejado.
2. **Nunca mentir ou fingir:** O agente NUNCA deve afirmar que algo está "perfeito", "idêntico às referências", "nível Awwwards" ou "100% pronto" se o resultado real for uma versão simplificada ou mediana.
3. **Autocrítica e Rigor Técnico:** Seja o primeiro a avaliar com honestidade e rigor se o código e o design realmente atendem ao nível exigido pelas referências enviadas pelo usuário (como Cipher.tv ou Maria João Abrantes).
4. **Transparência Total:** Se algo for difícil, se houver limitações ou se uma alteração não atingir o objetivo estético/funcional, diga a verdade de forma clara, direta e objetiva, apontando exatamente o que falta e como corrigir.
